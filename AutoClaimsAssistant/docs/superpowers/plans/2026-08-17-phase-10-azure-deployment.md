# Phase 10: Azure Deployment Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: superpowers:subagent-driven-development and superpowers:executing-plans are the defaults for this template, but **this project overrides that**: execute via **guided walkthrough** — present each step's snippet + file path/command in chat, the human creates/edits the file or runs the command themselves and reports the result back; do not use Write/Edit/Bash to create or modify source files, or to run any `az`/`docker`/`gh` command that provisions, modifies, or deletes a real resource, directly. Steps use checkbox (`- [ ]`) syntax for tracking progress across the walkthrough.

**Goal:** Make the roadmap's Phase 10 deliverable real: the containerized stack from Phase 9 (API + 3 MCP servers) running on Azure Container Apps, Blob Storage wired for claim document/photo uploads, and a GitHub Actions CD pipeline that deploys a canary revision receiving partial traffic before a manual promote-to-100% step — **defined as Infrastructure-as-Code (Bicep) so the whole compute/data layer can be deployed and torn down on demand**, not just stood up once by hand.

**Revision note (superseded a same-day first draft):** an earlier version of this plan used one-off imperative `az` commands for provisioning (Tasks 1-5) with no way to tear the stack down and bring it back except retyping every command by hand. Discussed with the project owner: the actual goal is a repeatable deploy/delete cycle so idle-but-billed resources (Postgres, ACR) aren't running between work sessions. This revision replaces that with Bicep templates + wrapper scripts. Two further decisions came out of that discussion, both verified during this replanning pass, not assumed:
1. **Azure OpenAI and Azure AI Search are captured in a separate, rarely-touched template (`platform.bicep`)**, not part of the routine teardown/redeploy cycle. Reasoning, confirmed against real state: recreating 7 OpenAI model deployments and re-indexing the policy corpus (Phase 4) is real, non-trivial rework, and neither resource actually costs anything sitting idle — Azure AI Search's Phase 4 `free` SKU is $0/month regardless of usage, and Azure OpenAI's `GlobalStandard` deployments are billed per-token with no idle charge. Postgres Flexible Server and ACR, by contrast, bill hourly/monthly whether or not anything is using them — those are the resources worth tearing down between sessions.
2. **`platform.bicep` was generated by decompiling the actual live resources**, not hand-written from memory: `az group export` + `az bicep decompile` against the real `claims-assistant-openai` and `claims-assistant-search` resources produced a template that is a byte-for-byte-accurate capture of what Phases 3/4 actually provisioned (exact model versions, exact SKUs, exact RAI policy config) — see Task 1.

**Architecture:** Four things were resolved by direct investigation during planning (real `az`/`az bicep` calls against the live subscription, real installed-SDK signature checks, and live web research), not assumed:

1. **Postgres cannot run as a Container App with mounted persistent storage.** Verified via research: Postgres needs to `chown` its data directory on startup, and Azure Files share mounts (the only persistent-volume option ACA supports) do not support `chown` — a widely-hit, documented failure. Postgres moves to **Azure Database for PostgreSQL Flexible Server**, Burstable `Standard_B1ms` tier (~$12-15/month) — verified available in `eastus2` via `az postgres flexible-server list-skus --location eastus2`. Local dev is unaffected — `docker-compose.yml`'s local `postgres` service stays exactly as Phase 9 left it.
2. **Registry: Azure Container Registry, not GHCR.** Confirmed with the project owner: ACR gives native managed-identity pull with no credential wiring. Name `claimsassistantacr` confirmed available via `az acr check-name`.
3. **Every Bicep template in this plan was validated against real ARM before being written into this document**, using `az deployment group validate` (a genuine server-side schema/RBAC check that creates nothing — confirmed non-mutating) and `az bicep build` (local syntax compile, zero network calls). Both `app-infra-base.bicep` and `app-infra-apps.bicep` (Task 2) validated clean on the first real pass; the one real bug this caught was in the *planning process itself*, not the templates — a naive "get my public IP" `curl` returned an IPv6 address on this network, which Azure Postgres firewall rules reject (IPv4 only). Task 2's deploy script uses an IPv4-only lookup (`https://api.ipify.org` over `-4`) instead.
4. **GitHub OIDC needs two distinct federated credentials, not one.** Verified via research: GitHub's OIDC token `sub` claim is `repo:<org>/<repo>:ref:refs/heads/main` for a normal job, but becomes `repo:<org>/<repo>:environment:<name>` for any job declaring `environment: <name>` — the promote step's manual-approval gate (a GitHub Environment) needs a credential matching that second form, or `azure/login` fails with an OIDC subject mismatch on that job specifically.

Once these are resolved, the shape is: a `platform.bicep` template capturing the already-provisioned OpenAI + Search (deployed rarely, mainly as a disaster-recovery/documentation artifact — it is *not* part of the routine cycle); two more templates, `app-infra-base.bicep` (ACR, Log Analytics, Container Apps environment, Postgres Flexible Server, Storage account) and `app-infra-apps.bicep` (the 4 container apps — split from `-base` because a container app's `image:` property needs an image that doesn't exist in ACR until *after* `-base` creates the registry and something pushes to it — a real sequencing constraint, not an arbitrary split); two PowerShell scripts orchestrating deploy and teardown of the app-infra layer (Postgres seeding included, since Bicep only creates empty resources); and the CD workflow from the original plan, unchanged in spirit — it still only builds/pushes images and updates container app revisions, per the project owner's explicit call to keep infra provisioning out of the push-triggered pipeline.

**Tech Stack:** New Python dependencies: `azure-storage-blob` (async client, `azure.storage.blob.aio.BlobServiceClient`), `python-multipart` (already present transitively via FastAPI's stack — version `0.0.32` confirmed installed — promoted to an explicit direct dependency). New Azure resources: everything under **Global Constraints** below. New tooling: Bicep CLI (`az bicep`, confirmed installed at `0.45.15` during planning). New GitHub Actions: a CD workflow (`auto-claims-assistant-cd.yml`) with a `production` GitHub Environment for the manual promote gate.

**Spec:** [docs/superpowers/specs/2026-08-10-auto-claims-assistant-design.md](../specs/2026-08-10-auto-claims-assistant-design.md) (§7 Deployment & CI/CD — this phase's primary scope; §5.1/§5.3 data & MCP — Postgres/MCP servers being deployed; §10 working agreement — guided walkthrough, no direct code writes, and no direct resource-provisioning commands run by the assistant either, per this plan's own override above)

## Global Constraints

- Python 3.12, src-layout under `src/claims_assistant/` (per Phase 0). Every I/O-bound function is `async def`.
- All Azure resources live in the existing `claims-assistant-rg` resource group, region `eastus2` (matching `claims-assistant-openai`; `claims-assistant-search` stays cross-region in `centralus` per Phase 4's documented fallback).
- **Resource inventory this phase manages, split by lifecycle:**
  - *Platform (rarely redeployed — not part of the app-infra teardown/redeploy cycle):* `claims-assistant-openai` (7 model deployments), `claims-assistant-search`. Originally provisioned by hand in Phases 3/4; `platform.bicep` (Task 1) captures them as code and — since the whole subscription was wiped mid-Phase-10 — is also what actually (re)created them, proving the disaster-recovery story it was written for.
  - *App infra (the actual deploy/teardown cycle):* `claimsassistantacr` (ACR), `claims-assistant-logs` (Log Analytics), `claims-assistant-env` (Container Apps environment), `claims-assistant-pg` (Postgres Flexible Server), `claimsassistantstorage` (Storage account + `claim-documents` container), and 4 container apps (`policy-db-mcp`, `claims-history-mcp`, `vin-vehicle-mcp`, `claims-assistant-api`).
- **Every Bicep template's API version was read live from `az provider show` during planning, not guessed**: `Microsoft.ContainerRegistry/registries@2026-03-01-preview`, `Microsoft.App/managedEnvironments@2026-03-02-preview`, `Microsoft.App/containerApps@2026-03-02-preview`, `Microsoft.DBforPostgreSQL/flexibleServers@2026-04-01-preview`, `Microsoft.Storage/storageAccounts@2026-04-01`, `Microsoft.OperationalInsights/workspaces@2026-03-01`, `Microsoft.CognitiveServices/accounts@2026-05-01`, `Microsoft.Search/searchServices@2026-03-01-preview`. The built-in `AcrPull` role definition ID (`7f951dda-4ed3-4680-a7ca-43fe172d538d`) was confirmed via `az role definition list --name AcrPull`, not recalled from memory.
- **No `az`, `docker push`, or `gh secret set`/`gh api` command that creates, modifies, or deletes a real resource is run by the assistant.** The read-only/non-mutating discovery commands that ground this document (`az resource list`, `az provider show`, `--help`, `az acr check-name`, `az postgres flexible-server list-skus`, `az bicep decompile`, `az deployment group validate`, `az role definition list`) already ran during planning; execution of this plan is 100% human-run, guided walkthrough.
- Every task ends with the relevant tests passing (and `uv run ruff check .` / `uv run mypy src` clean for touched source files) before moving to the next task.
- Every test that calls a real agent, real MCP server, real Postgres, or real Azure Blob Storage stays `pytest.mark.integration`.
- No secrets are ever committed to the repo. Cloud runtime secrets (Postgres password, Blob connection string, Azure OpenAI/Search keys) are Bicep `@secure()` parameters passed at deploy time, wired into Container Apps `secrets`/`secretRef`, never plaintext. CD-pipeline Azure auth is OIDC/federated-credential based.
- `docker-compose.yml` and local dev's `.env` defaults are **not** changed to point at cloud resources — local dev keeps its own containerized `postgres` service.

- [ ] **Step 2: Create `app-infra-apps.bicep`**

Also already validated against real ARM during planning. Create `AutoClaimsAssistant/iac/app-infra-apps.bicep`:

```bicep
// iac/app-infra-apps.bicep
// The 4 container apps. Deployed separately from app-infra-base.bicep because
// `image` must reference something that already exists in ACR -- run this only
// after app-infra-base.bicep has created the registry AND an image has been
// pushed to it (deploy-app-infra-apps.ps1 does both in the right order).

@description('Region for all resources in this template')
param location string = resourceGroup().location

@description('Image tag to deploy (e.g. a git short SHA) - image must already exist in ACR')
param imageTag string

@secure()
param postgresAdminPassword string

@secure()
param azureOpenAiApiKey string

@secure()
param azureSearchApiKey string

@secure()
param azureStorageConnectionString string

param azureOpenAiEndpoint string
param azureOpenAiApiVersion string
param azureSearchEndpoint string

var acrLoginServer = '${acr.name}.azurecr.io'
var image = '${acrLoginServer}/claims-assistant:${imageTag}'
var acrPullRoleId = subscriptionResourceId('Microsoft.Authorization/roleDefinitions', '7f951dda-4ed3-4680-a7ca-43fe172d538d')

resource acr 'Microsoft.ContainerRegistry/registries@2026-03-01-preview' existing = {
  name: 'claimsassistantacr'
}

resource containerAppsEnv 'Microsoft.App/managedEnvironments@2026-03-02-preview' existing = {
  name: 'claims-assistant-env'
}

// A single user-assigned identity shared by all 4 container apps for ACR pull.
// NOT system-assigned: a system-assigned identity's principalId only exists once
// the container app itself is created, so an AcrPull role assignment referencing
// it would depend ON the container app -- but the container app's first revision
// needs to pull its image (and thus needs the role already granted) before ARM
// considers it successfully provisioned. That circular dependency is a documented
// Azure Container Apps + Bicep limitation (fails with "Operation expired").
```

**Execution note (found and fixed during real Task 7 execution — this is a substantial, load-bearing change from the version validated during planning):** the original version above gave each of the 4 container apps its own `SystemAssigned` identity, with a per-app `AcrPull` role assignment referencing `<containerApp>.identity.principalId`. That validated cleanly (`az deployment group validate` doesn't catch this), but **failed on real deployment**, all 4 container apps identically, with `ContainerAppOperationError: Failed to provision revision... Operation expired`. Root cause, confirmed against real state and matched to a documented Azure Container Apps + Bicep limitation (Microsoft Q&A/GitHub issue #836): a system-assigned identity's `principalId` only exists once the container app itself is created, so the role assignment referencing it necessarily depends ON the container app — but the container app's first revision needs to pull its image (requiring the role to already be granted) before ARM considers it successfully provisioned. Circular, unresolvable in one flat deployment. Confirmed directly: `az role assignment list --resource-group claims-assistant-rg` showed zero `AcrPull` assignments after the failed run — they were never created, exactly as the circular dependency predicts.

**Fix:** replaced the 4 system-assigned identities + 4 per-app role assignments with **one shared user-assigned identity** (`claims-assistant-acr-pull-identity`) and **one role assignment**, both created before any container app (a user-assigned identity's `principalId` is known immediately, breaking the cycle). Each container app references it via `identity: { type: 'UserAssigned', userAssignedIdentities: {...} } }` and `registries[].identity: acrPullIdentity.id`, with an explicit `dependsOn: [acrPullRoleAssignment]`.

**Second issue hit even after that fix, on the very next real attempt:** 2 of 4 container apps still failed with the identical "Operation expired" error, while the other 2 succeeded — a genuine RBAC **propagation delay**, not the circular dependency (which the user-assigned identity fix did resolve — confirmed by the failure becoming partial/inconsistent instead of uniform across all 4). Azure role assignments are eventually consistent; even though the assignment is now correctly sequenced to exist before the container apps, the permission can take up to a couple of minutes to actually take effect everywhere, and ARM doesn't insert a wait. Fix: simply **retry the same `az deployment group create` command** — it's idempotent, the 2 already-succeeded apps are no-ops, and by the retry more real time had passed for the role to propagate, and the second attempt succeeded fully. If this recurs unreliably in the future, the deterministic fix would be splitting the identity+role-assignment into its own deployment step with a deliberate wait before deploying the container apps — not needed so far.

```python
from __future__ import annotations

import uuid

from azure.storage.blob.aio import BlobServiceClient

from claims_assistant.config import Settings


async def upload_claim_document(
    settings: Settings,
    claim_id: uuid.UUID,
    filename: str,
    content: bytes,
    content_type: str,
) -> str:
    blob_name = f"{claim_id}/{filename}"
    async with BlobServiceClient.from_connection_string(
        settings.azure_storage_connection_string
    ) as service_client:
        container_client = service_client.get_container_client(
            settings.azure_storage_container_name
        )
        blob_client = container_client.get_blob_client(blob_name)
        await blob_client.upload_blob(content, overwrite=True, content_type=content_type)
        return blob_client.url
```

Those three are always the *first* operation on a fresh session (called directly in `submit_claim`), so `session.begin()` works. `add_document_url` is different: the `upload_document` endpoint (Step 12) calls `get_claim_by_id(session, claim_id)` first, and that `session.get(...)` call triggers SQLAlchemy's **autobegin** — silently starting a transaction.
```yaml
# .github/workflows/auto-claims-assistant-cd.yml
name: AutoClaimsAssistant CD

on:
  push:
    branches: [main]
    paths:
      - "AutoClaimsAssistant/**"
      - ".github/workflows/auto-claims-assistant-cd.yml"

permissions:
  id-token: write
  contents: read

jobs:
  build-and-push:
    runs-on: ubuntu-latest
    outputs:
      image-tag: ${{ steps.sha.outputs.tag }}
    steps:
      - uses: actions/checkout@v4
      - id: sha
        run: echo "tag=$(git rev-parse --short HEAD)" >> "$GITHUB_OUTPUT"
      - uses: azure/login@v2
        with:
          client-id: ${{ secrets.AZURE_CLIENT_ID }}
          tenant-id: ${{ secrets.AZURE_TENANT_ID }}
          subscription-id: ${{ secrets.AZURE_SUBSCRIPTION_ID }}
      - run: az acr login --name claimsassistantacr
      - run: docker build -t claimsassistantacr.azurecr.io/claims-assistant:${{ steps.sha.outputs.tag }} AutoClaimsAssistant
      - run: docker push claimsassistantacr.azurecr.io/claims-assistant:${{ steps.sha.outputs.tag }}

  deploy-canary:
    needs: build-and-push
    runs-on: ubuntu-latest
    steps:
      - uses: azure/login@v2
        with:
          client-id: ${{ secrets.AZURE_CLIENT_ID }}
          tenant-id: ${{ secrets.AZURE_TENANT_ID }}
          subscription-id: ${{ secrets.AZURE_SUBSCRIPTION_ID }}
      - run: |
          az containerapp update \
            --name claims-assistant-api \
            --resource-group claims-assistant-rg \
            --image claimsassistantacr.azurecr.io/claims-assistant:${{ needs.build-and-push.outputs.image-tag }} \
            --revision-suffix ${{ needs.build-and-push.outputs.image-tag }}
      - run: |
          NEW_REVISION="claims-assistant-api--${{ needs.build-and-push.outputs.image-tag }}"
          OLD_REVISION=$(az containerapp revision list \
            --name claims-assistant-api --resource-group claims-assistant-rg \
            --query "[?properties.active && name!='$NEW_REVISION'].name | [0]" -o tsv)
          if [ -z "$OLD_REVISION" ]; then
            echo "No prior active revision found — first deploy, sending 100% traffic to $NEW_REVISION"
            az containerapp ingress traffic set --name claims-assistant-api --resource-group claims-assistant-rg --revision-weight "$NEW_REVISION=100"
          else
            az containerapp ingress traffic set --name claims-assistant-api --resource-group claims-assistant-rg --revision-weight "$NEW_REVISION=10" "$OLD_REVISION=90"
          fi

  promote:
    needs: deploy-canary
    runs-on: ubuntu-latest
    environment: production
    steps:
      - uses: azure/login@v2
        with:
          client-id: ${{ secrets.AZURE_CLIENT_ID }}
          tenant-id: ${{ secrets.AZURE_TENANT_ID }}
          subscription-id: ${{ secrets.AZURE_SUBSCRIPTION_ID }}
      - run: |
          NEW_REVISION="claims-assistant-api--${{ needs.build-and-push.outputs.image-tag }}"
          az containerapp ingress traffic set --name claims-assistant-api --resource-group claims-assistant-rg --revision-weight "$NEW_REVISION=100"
```

Note: `az containerapp update` targets a container app whose `revisions-mode` is already `Multiple` (set by `app-infra-apps.bicep`'s `activeRevisionsMode: 'Multiple'`) — no `az containerapp revision set-mode` step needed here, unlike a CLI-created app that defaults to `single`.

## Lessons Learned (2026-08-22 – 2026-08-23 execution session)

This phase's execution surfaced far more real, load-bearing bugs than any prior phase — worth a consolidated record, since several of them are exactly the kind of thing that would come up in an interview about this project's "productionizing" story: not just "I deployed to Azure" but "here's what actually breaks when you do, and why."

### Real bugs found in application code (not infra)

1. **Postgres DSN construction broke on a password containing `@`.** `config.py`'s `postgres_dsn`/`postgres_async_dsn` built connection strings via raw f-string interpolation (`f"postgresql://{user}:{password}@{host}:{port}/{db}"`). A password like `Admin@1234` produces a string with *two* `@` characters; `sqlalchemy.engine.make_url()` split on the *first* one, producing a garbage hostname (`1234@claims-assistant-pg.postgres.database.azure.com`) and silently truncating the password to `Admin`. This surfaced as `socket.gaierror` / `getaddrinfo failed` — a DNS resolution error that had nothing to do with DNS. **This cost the most debugging time in the whole session**: a real, multi-hour detour first suspected a Windows-asyncio-thread-pool DNS quirk (plain synchronous `socket.getaddrinfo()` calls with identical parameters succeeded every time, but the same call inside asyncio's executor failed — a genuinely reproducible, confusing signal that pointed the wrong way), then suspected Docker Desktop's embedded DNS resolver when the same symptom reproduced inside a Linux container. The actual fix (`urllib.parse.quote(value, safe="")` on both `postgres_user` and `postgres_password` before interpolating) was only found by testing the *exact* failing DSN string through `make_url()` directly and reading its output — not by reasoning about networking at all. **Lesson: when an error message is confidently specific ("DNS resolution failed") but a change of runtime/OS doesn't change the symptom, question whether the layer producing the error message is even the layer with the actual bug** — here, the error surfaced deep in asyncpg/asyncio, but the defect was in URL string construction two layers up.
2. **`add_document_url`'s `session.begin()` conflicted with SQLAlchemy's autobegin.** The `upload_document` endpoint calls `get_claim_by_id` (a `session.get(...)` call) before `add_document_url` — and any query on a `Session`/`AsyncSession` triggers autobegin, silently starting a transaction. `add_document_url`'s `async with session.begin():` (copied from `create_completed_claim`'s pattern, which is always the *first* thing to touch its session) then failed with `InvalidRequestError: A transaction is already begun on this Session`. Fix: don't re-begin — mutate the already-tracked object and call `session.commit()` directly. **Lesson: a repository-layer helper pattern that works for one call site isn't automatically safe for another — the assumption "this session is fresh" needs checking per call site, not copy-pasted.**
3. **Schema drift with no migration tool.** `create_all_tables()`'s `Base.metadata.create_all()` only creates missing tables; it never alters existing ones. Adding `document_urls` to the `Claim` model did nothing to the `claims` table already sitting in Azure Postgres from an earlier seeding run. Every prior phase (0-9) happened to always run against a genuinely fresh database, so this had never come up. Fix here was a manual `DROP TABLE claims` (safe — it only ever held pipeline results, not seed data) and letting `create_all_tables()` recreate it. **This is a real, durable gap in the project, not just a one-off annoyance** — worth flagging as a known limitation if this project's schema evolves further: either adopt Alembic, or keep accepting manual drops as the "migration strategy" for a demo project.

### Real bugs found in the Bicep/infra design

4. **Circular dependency: system-assigned identity + same-deployment `AcrPull` role assignment.** Each container app's `AcrPull` role assignment referenced `<containerApp>.identity.principalId` — but a system-assigned identity's `principalId` only exists once the container app itself is created, and the container app's first revision needs to *already* have pull permission to be considered successfully provisioned. All 4 container apps failed identically with `Operation expired` on the first real deploy attempt. This is a **documented Azure Container Apps + Bicep limitation** (confirmed via Microsoft Q&A and `microsoft/azure-container-apps` GitHub issue #836) — not something `az deployment group validate` catches, since it's a runtime provisioning-order problem, not a schema error. Fix: one shared **user-assigned** identity, created (and granted the role) before any container app exists, referenced by all 4 via `identity.type: 'UserAssigned'`. **Lesson: `az deployment group validate` proves your template is well-formed ARM, not that the resources will actually provision successfully — some failure modes only exist at real-deployment time, especially around identity/RBAC timing.**
5. **RBAC propagation delay, even after fixing #4.** The very next real attempt still failed 2-of-4 container apps identically (`Operation expired`) — but the *other* 2 succeeded, which is the tell that the circular dependency was actually gone (a real circular dependency fails uniformly; this was inconsistent). Azure role assignments are eventually consistent; the permission can take up to a couple of minutes to actually take effect even once correctly sequenced. Fix: just retry the same (idempotent) deployment command — enough real time had passed for propagation to catch up, and it fully succeeded. **Lesson: distinguish "wrong dependency order" (deterministic, same failure every time) from "right order but propagation lag" (intermittent/partial failure) before reaching for a bigger fix** — the second one often just needs a retry or a deliberate wait, not a redesign.
6. **GitHub Actions job outputs are not transitive across a `needs:` chain.** `promote` had `needs: deploy-canary` (correct, since it must run after it) but tried to read `needs.build-and-push.outputs.image-tag` — which resolves to empty, because a job can only see outputs from jobs it *directly* lists in its own `needs:`, regardless of what its dependencies themselves depend on. Fix: `needs: [deploy-canary, build-and-push]`. **This is a well-known GitHub Actions gotcha, easy to write correctly-looking YAML that's subtly wrong** — worth remembering for any future multi-stage workflow with output passing.

### Environment/tooling gotchas (not bugs in our code, but cost real time)

7. **Azure OpenAI real-time fraud protection (RTFP), error `715-123420`.** Deleting and recreating the same Azure OpenAI resource triggered an account-level fraud flag that blocks resource creation entirely, confirmed via research to be evaluated at the subscription/account level (a fresh resource group did *not* help, per a matching report from someone else who hit the identical error). No config change, retry, or region switch lifts it — only a support ticket reviewed by Azure's account-protection team does, and that requires the **Portal UI**, not the CLI (`az support in-subscription tickets create` requires a paid support plan; Billing-category tickets are free only through the Portal). Still unresolved as of this session's end — genuinely external, not something to keep re-attempting.
8. **PowerShell mangles embedded double-quotes when passing JSON strings to native executables.** `az ad app federated-credential create --parameters '{"name":"..."}'` had its quotes stripped by PowerShell before `az.exe` ever saw them. Fix: write the JSON to a file with `Out-File` (pure PowerShell string handling, no native-exe argument marshaling involved) and pass `--parameters @filename.json` instead. **A generically useful pattern for any future PowerShell + CLI-tool-expecting-JSON situation.**
9. **PowerShell session variables silently going stale across a long session.** `$sha`, `$storageConn`, and `$app.appId` (used to set `AZURE_CLIENT_ID`) all caused real failures when their values turned out to be empty or from an old commit — either because a new terminal window was opened, or because enough time/commands had passed that the "obvious" assumption ("that variable is still set correctly") silently stopped holding. Each time, the fix was cheap (re-fetch fresh), but each also cost a full debug cycle to notice. **Lesson for any long guided session using shell variables as informal state: when a value that "should" be set produces a confusing downstream error (empty image tag, empty secret, empty container app parameter), check the variable's actual current value before debugging the consumer of that value.**
10. **My own copy-paste bug while rewriting `app-infra-apps.bicep`:** moved `activeRevisionsMode` out of the `configuration` block on the `api` resource, making it an invalid sibling property. Caught immediately by `az deployment group validate` (`ContainerAppInvalidSchema`) before it ever reached a real deployment attempt — the cheap validation step did its job here, unlike issue #4 which validation couldn't catch.
11. **Azure AI Search indexing latency on a freshly created index, immediately after the subscription-wipe re-provisioning.** Re-running Task 1 Step 6 (`tests/test_indexer.py`) against the newly recreated `claims-assistant-search` failed on its first attempt: `indexed_count == 63` passed (meaning `upload_documents()` was accepted without error) but the very next assertion — a live `search_text="*"` query for `total` — returned `0`. Root cause: `index_policy_corpus()` calls `create_or_update_index()` (creating the index schema from nothing, since the service was brand new) immediately followed by the document upload in the same function; Azure AI Search indexing is near-real-time, not synchronous, and the first write to a just-created index appears to take measurably longer to become queryable than a write to an already-warm index — the test's second assertion ran before that initial propagation finished. Confirmed as latency, not a real failure: rerunning the identical test moments later (no code or data change) passed both assertions — the same 63 documents from the first run had already landed and simply finished propagating, `upload_documents()` being idempotent/upsert on retry either way. **Lesson: this is the same category as issue #5 (RBAC propagation) — an eventually-consistent Azure service catching a check that ran one beat too early. Before treating a `0`-count/empty-result failure as a real bug, check whether it's the very first read immediately following the very first write to a brand-new resource, and just retry once before investigating further.**
12. **`teardown-app-infra.ps1` didn't delete `claims-assistant-acr-pull-identity`, orphaning it on every teardown.** The script (Task 2) was written before the system-assigned → shared user-assigned identity fix (issue #4 above) existed; that fix added a new top-level resource, `Microsoft.ManagedIdentity/userAssignedIdentities/claims-assistant-acr-pull-identity`, created by `app-infra-apps.bicep`. Because it's an independent top-level resource (not a child of the ACR or any container app), deleting the ACR/container apps/environment didn't take it with it, and the teardown script's list of `az ... delete` calls was never updated to include it. Confirmed directly: after a real teardown + `az resource list --resource-group claims-assistant-rg`, the identity was the only app-infra resource still present alongside the two platform resources. Practically low-risk — `app-infra-apps.bicep`'s `create_or_update` semantics mean a stale identity wouldn't have broken the next redeploy, just left an orphaned resource behind indefinitely — but it directly contradicted the script's own header comment ("Deletes everything deploy-app-infra-base.ps1 / -apps.ps1 created"). Fixed by adding an `az identity delete --name claims-assistant-acr-pull-identity --resource-group claims-assistant-rg` step to the script. **Lesson: when a later fix during real execution adds a new standalone resource to one script (the deploy side), audit every other script that's supposed to fully reverse it (the teardown side) — Bicep's own `dependsOn`/parent-child relationships won't catch a resource deletion gap that a hand-maintained imperative script has to track manually.**
13. **`app-infra-apps.bicep`'s `api` container app was missing `AZURE_OPENAI_CHAT_DEPLOYMENT` entirely.** `extraction_agent.py`'s `build_chat_client` reads `settings.azure_openai_chat_deployment` (default `""`) as the `model` passed to `OpenAIChatCompletionClient` — but the Bicep template's env list wired `AZURE_OPENAI_COVERAGE_DEPLOYMENT`, `AZURE_OPENAI_EMBEDDING_DEPLOYMENT`, `AZURE_OPENAI_FRAUD_DEPLOYMENT`, and `AZURE_OPENAI_ADJUSTER_SUMMARY_DEPLOYMENT`, but never `AZURE_OPENAI_CHAT_DEPLOYMENT` (the `extraction-agent` deployment). Every real `POST /claims` against the deployed API failed with `agent_framework.exceptions.SettingNotFoundError: Azure OpenAI client requires a model...`, caught via the Portal's Log Stream. This bug existed in the template since Task 2 and was never caught during the original Task 7 deployment — because Task 1 (real OpenAI) was blocked by the RTFP support ticket for the entirety of last session, so the deployed API's `/claims` endpoint was never actually exercised end-to-end with real credentials before; only `/health` was verified live, and Task 5's API test was deliberately rewritten to bypass the agent entirely (`create_failed_claim`) to avoid depending on the blocked OpenAI resource. This session's platform-layer-manual-creation-then-redeploy was the first time real credentials and a real `/claims` call ever met the deployed container. Fix: add `{ name: 'AZURE_OPENAI_CHAT_DEPLOYMENT', value: 'extraction-agent' }` to the `api` container's env list, then rerun `deploy-app-infra-apps.ps1` (no image rebuild strictly required for an env-var-only Bicep change — a targeted `az deployment group create` would suffice — but rerunning the full script is harmless and simpler). **Lesson: an infra template can validate clean, deploy clean, and pass every check that doesn't require the specific downstream credential/config it's silently missing — `/health` endpoints are not a substitute for exercising the actual golden-path request once the real dependency it needs is finally available. A "verified working" claim made while a dependency was known-blocked should be treated as partially verified, not fully verified, and revisited once that dependency clears.**
14. **Deleting and recreating a single resource (the ACR) inside an otherwise-intact resource group silently broke CD, exactly like a full resource-group deletion does.** After this session's Task 9 teardown/redeploy proof (which deletes and recreates `claimsassistantacr` as part of the normal app-infra cycle), the very next CD push failed at `az acr login` with a 401 / "resource could not be found" — the GitHub Actions service principal's `AcrPush` role assignment, scoped to the ACR resource specifically, had been deleted along with the ACR and never recreated (it was originally a one-time manual step from Task 6, entirely outside Bicep's management). This is the same underlying mechanism as issue #9/the earlier resource-group-deletion case, but narrower and easier to miss: no RG deletion is needed to trigger it, just tearing down and recreating the one resource the role assignment happens to be scoped to. Fix: moved the `AcrPush` role assignment into `app-infra-base.bicep` itself (a new `githubActionsSpObjectId` param + an `acrPushRoleAssignment` resource scoped to the `acr` resource, deployed alongside it), so every `deploy-app-infra-base.ps1` run — including the one right after a teardown — regrants it automatically instead of depending on someone remembering a separate manual step. **Lesson: any role assignment scoped to a resource that a teardown/redeploy cycle destroys and recreates needs to live in the same IaC template as that resource, not be a one-off manual grant — otherwise every full cycle silently regresses CD (or whatever else depends on that grant) until someone notices a failure downstream.**
15. **Fixing #14 itself hit two more real, chained bugs on the first attempt.** First, `az deployment group create` failed with `RoleAssignmentExists`: the manual role assignment created earlier in this same session (via `az role assignment create`, which auto-generates a random assignment name) and Bicep's new `acrPushRoleAssignment` resource (named deterministically via `guid(acr.id, githubActionsSpObjectId, 'AcrPush')`) both targeted the identical principal+role+scope — Azure rejects a second role assignment for that exact combination regardless of the assignment's own name, so the deployment failed even though nothing was semantically wrong with the template. Fix: delete the old manually-named assignment first (`az role assignment delete --assignee ... --role AcrPush --scope ...`), then let Bicep create its own. Second, and non-obvious: because that deployment failure meant `az deployment group create`'s `--query "properties.outputs"` returned nothing, `deploy-app-infra-base.ps1`'s `$deployment.postgresFqdn.value` evaluated to `$null` — and in PowerShell, `$env:POSTGRES_HOST = $null` doesn't set the variable to an empty string, it **deletes the environment variable entirely**. With `POSTGRES_HOST` unset, `Settings` fell back to its local-dev default (`postgres_host: str = "localhost"`, `config.py:12`), and since the script also force-sets `POSTGRES_SSL_MODE=require`, `seed_db.py` tried an SSL handshake against `localhost:5432` and failed with `ConnectionError: ... rejected SSL upgrade` — a misleading error with nothing to do with SSL configuration itself; the real problem was three layers upstream (a role-assignment naming conflict) and one PowerShell semantics quirk away. Confirmed no actual resources were harmed: ACR/Postgres/Storage/Log Analytics/Container Apps environment all already existed and were no-ops in that deployment attempt — only the new role assignment resource failed, which was enough to fail the whole deployment and blank out its outputs. **Lesson: when a script chains `az deployment group create`'s outputs directly into environment variables consumed by a later step, a partial/failed deployment doesn't just skip that later step — in PowerShell specifically, it can silently redirect it at a wrong-but-valid default (here, local dev Postgres) and produce an error that looks unrelated to the actual root cause. Trace failures like this backward through every layer (deployment status → CLI query output → PowerShell variable assignment → env var → application default) rather than debugging the symptom (the SSL error) in isolation.**

### What worked well, worth repeating

- **Validating every Bicep change against real ARM (`az deployment group validate`) before handing it to the user**, even when the change felt small — caught the `activeRevisionsMode` typo for free, at zero cost, before it could cost a real deployment cycle.
- **Reproducing a failing call with a synchronous, minimal, single-purpose script** (plain `socket.getaddrinfo()`, plain `asyncpg.connect()` bypassing SQLAlchemy, `make_url()` on the literal failing DSN string) was what actually found both the DSN bug and confirmed the identity/RBAC fix's real cause — narrowing to the smallest reproduction consistently beat reasoning about the failure in the abstract.
- **Treating a task's own "don't do X" instruction as revisable, not sacred, once real execution proves the premise wrong** — Task 1 originally said "never redeploy `platform.bicep`, it's disaster-recovery only"; the subscription wipe made that premise false, and the plan was rewritten (not just worked around) to reflect the new reality.
