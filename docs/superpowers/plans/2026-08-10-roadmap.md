# Implementation Roadmap — AI-Powered Auto Insurance Claims Assistant

**Source spec:** [docs/superpowers/specs/2026-08-10-auto-claims-assistant-design.md](../specs/2026-08-10-auto-claims-assistant-design.md)

This roadmap lists all implementation phases at a high level. Each phase gets its own fully-detailed, bite-sized implementation plan written **just before that phase starts** (not now) — so later-phase plans benefit from what earlier phases actually taught us, rather than locking in details prematurely.

**Execution model:** Guided walkthrough. For each phase's plan, work through it conversationally — code is given as snippets to create/edit yourself; you run tests/commands and report results back. See the working agreement in the design spec (Section 10).

## Phases

| # | Phase | Deliverable | Success Criteria |
|---|---|---|---|
| 0 | **Foundations** | Repo scaffolding: FastAPI skeleton, config, Docker Compose (Postgres), lint/typecheck/test tooling | `uvicorn` runs, `GET /health` responds, `pytest` runs (even if trivial), `docker-compose up` brings up Postgres reachable from the app |
| 1 | **Synthetic data generation** | Synthetic policy documents (8–12), seeded Postgres (policies, claims history, VIN/vehicle), FNOL extraction eval fixtures with gold JSON | Seed script populates Postgres deterministically; policy corpus + eval fixtures checked into repo |
| 2 | **MCP servers** | `policy-db-mcp`, `claims-history-mcp`, `vin-vehicle-mcp` — each independently runnable and tool-callable | Each MCP server responds correctly to a manual tool call against the seeded data (e.g. via an MCP inspector/test client) |
| 3 | **Extraction Agent** | Microsoft Agent Framework agent: FNOL text → fixed Pydantic JSON schema, few-shot prompting, per-field confidence | Runs against sample FNOL text and produces schema-valid JSON; passes a first cut of the extraction eval fixtures from Phase 1 |
| 4 | **Azure AI Search indexing + Coverage Agent** | Policy corpus indexed into Azure AI Search; Coverage Agent does grounded RAG with citations | Given a claim + policy, returns approve/deny/needs-info with a citation that traces to a real indexed chunk |
| 5 | **Fraud-Risk Agent** | Agent that calls `claims-history-mcp` + `vin-vehicle-mcp`, reasons over red flags, returns score + rationale | Rationale is traceable to actual tool-returned data on a handful of test cases (one clean, one flagged) |
| 6 | **Supervisor orchestration graph** | Microsoft Agent Framework workflow graph wiring: sequential backbone, parallel fan-out (Coverage + Fraud), confidence-based handoff to clarification path, Adjuster-Summary Agent | End-to-end graph run on a sample FNOL produces a merged adjuster-summary output; a deliberately low-confidence input routes to the clarification path instead |
| 7 | **FastAPI orchestrator endpoints** | `POST /claims`, `GET /claims/{id}` wired to the workflow graph | A real HTTP request through Swagger/Postman runs the full pipeline and returns the structured recommendation |
| 8 | **Eval framework** | pytest-based harness: deterministic extraction scoring, LLM-as-judge for coverage grounding + fraud rationale, Pandas aggregation report, baseline thresholds | Running the eval suite locally produces a scored report; intentionally breaking a prompt drops a score below baseline and the harness flags it |
| 9 | **Containerization & CI** | Dockerfiles per service, GitHub Actions pipeline (lint → test → eval gate) | A PR with a deliberately regressive prompt change fails CI at the eval-gate step; a clean PR passes all steps |
| 10 | **Azure deployment** | Azure Container Apps deployment (API + MCP servers), Blob Storage wiring, canary revision + promote step | Service reachable at a public Container Apps URL; canary revision receives partial traffic before promotion |

## Dependencies between phases

- Phase 0 blocks everything (nothing runs without it).
- Phase 1 (synthetic data) blocks Phase 2 (MCP servers need data to serve) and the eval portions of Phase 3/4/5 (need fixtures/corpus).
- Phases 3, 4, 5 (the three specialist agents) are independent of each other once Phase 1 + relevant Phase 2 MCP servers exist — Coverage Agent (Phase 4) doesn't need the Fraud-Risk Agent (Phase 5) built first, for example.
- Phase 6 (orchestration graph) depends on Phases 3, 4, 5 all existing.
- Phase 7 (API) depends on Phase 6.
- Phase 8 (eval framework) can start as soon as Phase 1 fixtures exist, and is extended incrementally as each agent (3/4/5) comes online — it doesn't strictly wait for Phase 7.
- Phases 9–10 (CI/CD, deploy) depend on there being something real to containerize and test — practically, after Phase 7 and a working Phase 8.
